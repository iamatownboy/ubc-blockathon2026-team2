### 마지막 보완 — 실패한 교환에 종결 상태 되돌리기

제공사 모호성 처리를 강화하면서 한쪽으로 넘어간 부분이 있었습니다. 실패 모드
네 개(`error` 502, `timeout`, `ghost`, `httpghost`)가 **전부 "모호"로 분류**되고,
관리자 reconcile은 주문을 못 찾으면 환불하지 않고 끝나서, **서비스에서 학습자가
크레딧을 돌려받는 경로가 하나도 남지 않았습니다.** 환불 로직 자체(컨트랙트·원장의
`cancelSwap`)는 멀쩡했지만 거기에 도달할 방법이 없었습니다.

보안 판단은 옳았습니다 — 카드와 환불을 동시에 주면 안 되니까요. 다만 실패한
교환에 종결 상태가 없어지는 대가를 치렀습니다. "제공사가 하루 죽으면?"의 답이
"크레딧 소멸, 카드 없음, 운영자도 못 고침"이 됩니다.

**1. 목업 제공사에 `declined` 모드 추가.** 발급사가 `422 order_declined`로
답하는, 계약이 정의한 확정 실패입니다. 클라이언트는 이미 4xx를 확정 실패로
분류하므로 코드 변경 없이 환불 경로가 되살아났고, 무엇보다 **시연이 가능해졌습니다.**
발표에서 장면이 둘이 됩니다 — 모호하면 붙잡고, 확정 거절이면 돌려줍니다.

**2. 관리자 콘솔에 reconcile과 분리된 환불 버튼.** 제공사가 조용해진 뒤 끝내
돌아오지 않는 교환은 기계가 종결할 수 없어서 사람이 합니다. 두 버튼은 의미가
다릅니다 — reconcile은 제공사에 다시 묻고, refund는 제공사가 뭐라고 했는지를
운영자가 단언합니다. 라우트는 `confirmedNoOrder: true` 없이는 `422`로 거부하고,
실행 직전 한 번 더 조회해 주문이 있으면 **환불 대신 카드를 전달**하며,
`swap.force_refunded`로 결정을 기록합니다.

테스트 `18b`(확정 거절 → 정확한 환불), `18c`(모호 → 보류 → 단언 없는 환불 거부 →
단언 후 종결), `18d`(카드가 있으면 강제 환불도 거부)가 셋 다 고정합니다.

| 체인 모드 전체 흐름 | 미션 → 중복 거부 → 두 번째 미션 → 교환 → 정산, `ledgerMode=chain` 확인 |
| 브라우저 초기화 후 재파밍 | 차단 확인 (같은 핸들, 잔액 0, `already_completed`) |

Solidity 테스트는 네트워크가 없는 환경에서 `SOLC_JS=1 npx hardhat test`로
node_modules의 solcjs를 써서 검증했습니다.

## 발표 때 보여줄 것

가장 잘 먹힐 시연은 **"한 사람이 반복해서 빼갈 수 있나"** 입니다.
`/demo/` 를 띄워놓고: 미션 완료 → 카드 교환 → 브라우저 데이터 삭제 → 같은 참여
코드 재입력 → "이미 완료한 미션" 화면. 왼쪽에서 크레딧이 지급되는 순간 오른쪽
원장에 이벤트가 찍히는 것을 같이 보여주면, 포괄성(계정 없이 종이 코드만)과
보안(평생 한도가 사람 단위)을 한 번에 짚습니다.

## 남은 한계 (심사위원이 먼저 찾기 전에 밝힐 것)

- 참여 코드의 실효성은 파트너의 배부 관리에 달려 있습니다. 한 사람에게 두 장이
  가면 이 서비스에는 두 명입니다. 코드 발급 기록은 파트너 측 책임입니다.
- 카드는 코드를 마지막으로 사용한 기기 키로 봉인됩니다. 새 기기에서 코드를
  다시 입력하면 잔액은 복구되지만 이전 기기 키로 봉인된 카드는 열리지 않습니다.
- 기프트카드 제공사는 여전히 목업입니다. 실제 연동에는 업체 계약, 프로그램 승인,
  상품 구성, 인증서 설정이 필요합니다.
- `admin-demo` / `verifier-demo` 토큰은 공개돼 있습니다. 로컬 전용이며 운영
  모드에서는 서버가 거부합니다.
- 검증자 키는 하나입니다. 미션 레지스트리가 이를 견딜 만하게 만들 뿐,
  괜찮게 만들지는 않습니다.
- `/demo/` 화면은 구조 검증만 했고 실제 렌더링은 확인하지 못했습니다.
  한 번 열어보고 레이아웃을 확인해주세요.

## 2026-08-28 추가 보강

- 검증자 화면이 열리자마자 멈추던 `$` 헬퍼 누락을 고치고, 같은 문제가 돌아오지
  않도록 브라우저 스크립트를 실제 실행하는 UI 스모크 테스트를 추가했습니다.
- 학습자 공개 키는 P-256 JWK로 실제 파싱된 뒤에만 세션을 만들도록 했습니다.
- 운영 모드는 신원 비밀값과 두 역할 토큰을 각각 32바이트 이상으로 요구하고,
  관리자와 검증자 토큰 재사용도 거부합니다. 역할 토큰은 URL로 받지 않으며,
  이벤트 스트림은 1분짜리 일회용 티켓을 사용합니다.
- 만료된 검토 항목은 직접 API를 호출해도 승인하거나 보상할 수 없습니다.
- 제공사의 타임아웃과 HTTP 5xx를 '발급됐을 수도 있는 결과'로 취급합니다. 조회의
  `없음`도 지연 반영일 수 있으므로 명시적인 최종 실패가 아니면 Requested 상태로
  보류해 카드와 환불이 동시에 생기는 일을 막습니다.
- 메모리 원장 패리티 테스트의 상품 코드 인코딩을 실제 배포 스크립트와 같은
  `bytes32` ASCII 방식으로 통일했습니다. 로컬 Hardhat 체인과 전체 기록 비교가
  통과합니다.

현재 자동 검증 기준은 원장 28개, E2E 50개, UI 스모크 2개, 패리티 1개,
Solidity 23개입니다. 위의 `/demo/` 미확인 메모는 8월 27일 시점 기록이며,
8월 28일에는 검증자·관리자 흐름을 포함한 브라우저 확인을 다시 수행했습니다.
